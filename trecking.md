# ЗАДАНИЕ: трекинг

## АНАЛИЗ РИСКОВ И ОБНОВЛЕНИЕ ГРАФИКА

**Отчетный период:** первые 1.5 месяца разработки

В данный период произошло **срабатывание трех рисков**, что вызвало каскадный эффект задержек.

### 1. Анализ рисков

#### Риск №1: Некорректная работа терморегуляционной модели
*   **Ситуация:** На внутренних тестах выяснилось, что ML-модель игнорирует ветер и влажность. При +10°C модель советует легкую одежду, что является критическим багом алгоритма.
*   **Влияние:** ML-команда не может сдать очередной этап. Им требуются новые данные от Бэкенда (параметры ветра в API), чтобы переобучить модель.
*   **Последствия:** Блокировка релиза модели. Запрос на доработку Бэкенда.

**Временные потери:**

- Доработка данный с бэкенда ~ 3-5 дней
- Перестроение и обучение модели с новыми данными ~ 2 недели

накопившееся отставание от графика: 2,5 недели

#### Риск №2: Болезнь ведущего Backend-разработчика (Team Lead)
*   **Ситуация:** Тимлид, единственный единственный, кто разбирается во всех компонентах, заболевает и отсутствует **2 недели**.
*   **Влияние:**
    *   Мискомуникация внутри команды, так как не все осведомлены о всех тонкостях проекта
    *   Некому провести Code Review сложных задач.
    *   Младшие разработчики остаются без технического надзора.
*   **Последствия:** **Сильная задержка** критических задач сервера, так как необходимо в разы больше времени чтобы организоваться и согласовать все детали

**Временные потери:**
при условии того, что тимлид болеет неделю, считаем что застой произошел как раз на эту неделю (запланированные задачи либо не доделались до конца, либо требует проверки тимлидом и дальнейшей доработки)

#### Риск №3: Некорректные данные API погоды и недоступность
*   **Ситуация:** На очередном тесте было замечено, что внешнее API погоды отключилось на некоторое время, из-за чего наше приложение не получало корректные данные.
*   **Влияние:** Необходимо либо менять API либо продумывать логику работы при временном отключении доступа с внешнему API (запрашивать данные наперед, добавлять более умное кэширование).
*   **Последствия:** требуется выделить время на обсуждение и доработку ~ 2 недели. Не отдаем данные смежной команде мобильной и фронтенд разработки всрок

**Временные потери:**
примерно 2 недели

### 2. Оценка потерь

**Общий временной сдвиг (Time Delay):**
Риски привели к следующим результатам на Бэкенде.
*   **Этап 6.1 (Сервер):** 1 неделя (болезнь Лида) + 2 недели (смена API и помощь ML) + 2 недели прорыботки сценария отключения внешнего API = **~4 недели (35 дней)** задержки.
*   **Этап 6.2 (Мобильное ПО):** Простой в ожидании рабочего API = **~25 дней**.
*   **Этап 6.5 (ML):** Переобучение модели после получения данных = **14 дней**.

**Финансовые потери:**
*   Зарплаты на дополнительный месяц: **2 000 000 руб.** (команда разработки ~ 15 человек)
*   Вероятная смена погодного API и покупка платной лицензии: **150 000 руб.**
*   Исправление модели ML: **100 000 руб.**
*   **ИТОГО:** ~**2 000 250 руб.**


**Вывод:** Проект нуждается в выделении резервного бюджета (680 тыс. руб.) и срочном подключении коммерческого API погоды для разблокировки работы команд.
