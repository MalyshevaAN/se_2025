# План тестирования АС "SmartCloth"


## 1. Стратегия и Цели тестирования

### Цели
1. Подтверждение функциональной полноты согласно ТЗ (особенно разделы 4.2.1–4.2.5).
2. Проверка надежности (доступность 99.5%, восстановление < 2 ч).
3. Обеспечение безопасности пользовательских данных (ФЗ-152, On-device privacy).
4. Валидация качества ML-алгоритмов (точность рекомендаций > 80%).

### Объекты тестирования
*   **Мобильные клиенты:** iOS (14+), Android (8.0+).
*   **Backend:** API Gateway, микросервисы (Auth, Weather, Recommendation, Wardrobe, 3D).
*   **Интеграции:** Внешние погодные провайдеры, каталоги партнеров.
*   **ML-модели:** Персональная термомодель, Computer Vision для распознавания одежды.

---

## 2. Виды и Уровни тестирования

### Функциональное тестирование
*   **Smoke-тестирование:** Регистрация, главный экран, получение базовой рекомендации.
*   **Критический путь:** Настройка профиля -> Загрузка гардероба -> Получение рекомендации -> Feedback.
*   **Офлайн-режим:** Работа с кэшированными данными (согласно п. 4.1.2).

### UI/UX и Кроссплатформенность
*   Адаптивность верстки.
*   Отображение 3D-моделей на разных мобильных устройствах.
*   Доступность и локализация.

### Производительность (Performance)
*   Нагрузочное тестирование API (ожидаемое время отклика < 3 сек).
*   Стресс-тестирование при пиковых нагрузках (утренние часы).

### Тестирование данных и ML
*   Проверка корректности построения термомодели.
*   Точность распознавания фото одежды.

---

## 3. Инструментарий (согласно стеку в ТЗ)
*   **Управление тестами:** TMS (TestRail/Allure).
*   **API тестирование:** Postman / Swagger, Python (Pytest).
*   **Нагрузка:** JMeter / Locust.
*   **Мобильная автоматизация:** Appium.
*   **Снифферы трафика:** Charles / Wireshark (для проверки безопасности).

---

## 4. Сценарии тестирования 

Распределение задач для кросс-функциональной команды QA с привязкой к конкретным пунктам ТЗ.

### №1 Малышева Анастасия
**Задача:** Проверка ключевого бизнес-процесса персонализации.

#### Сценарий: "Корректировка термомодели на основе обратной связи"
1.  **Предусловие:**
    *   Пользователь авторизован.
    *   Создан базовый профиль (чувствительность "Нормальная").
    *   Установлена геолокация с погодой +10°C.
    *   Система выдала рекомендацию: "Ветровка + Футболка".
2.  **Шаги:**
    *   В интерфейсе оценки образа нажать кнопку "Мне было холодно".
    *   Дождаться обновления данных (синхронизация термомодели).
    *   Запросить рекомендацию заново для *тех же* погодных условий (+10°C).
3.  **Ожидаемый результат:**
    *   Сбор фидбека прошел успешно.
    *   Новая рекомендация изменилась на более теплую (например, добавился "Свитшот" вместо футболки или "Утепленная куртка").
    *   В профиле пользователя (в backend-логах) изменился коэффициент тепловосприятия.

### № 2 Бурмистрова Юлия
**Задача:** Обеспечение надежности при сбоях внешних систем
(погода).

#### Сценарий: "Отказ погодного провайдера и работа кэша"
1.  **Предусловие:**
    *   Пользователь имеет подписку Premium (прогноз на 5 дней).
    *   Данные погоды успешно загружены и закэшированы в Redis/локально.
    *   Инструментально заблокировать доступ сервера/приложения к внешнему API погоды (имитация 500 error / Timeout).
2.  **Шаги:**
    *   Запросить обновление рекомендаций на "Завтра".
3.  **Ожидаемый результат:**
    *   Приложение **не** падает с ошибкой.
    *   Рекомендация строится на основе данных из кэша.
    *   Пользователь видит UI-уведомление: "Данные погоды могут быть неактуальны (обновлено: [время])".
    *   Время формирования ответа не превышает 3 секунды.

### № 3 Головачев Сергей
**Задача:** Проверка требований к быстродействию.

#### Сценарий: "Spike-тестирование: Утренний пик активности"
1.  **Предусловие:**
    *   Нагрузочный скрипт (JMeter/Locust) имитирует поведение 5000 пользователей.
    *   Сценарий: Вход -> Получение геопозиции -> GET /recommendation.
2.  **Шаги:**
    *   Запустить резкую подачу нагрузки (ramp-up 1 минута) в эмуляции временного интервала 07:30–08:00 утра.
3.  **Ожидаемый результат:**
    *   95-й перцентиль времени отклика (p95) < 3000 мс.
    *   Процент ошибок (HTTP 5xx) < 0.5%.
    *   Автоскейлинг микросервисов в Kubernetes (если применимо) срабатывает корректно, добавляя поды.

### № 4 Артамонова Анна
**Задача:** Проверка "Умного гардероба".

#### Сценарий: "Автоматическая классификация загруженной одежды"
1.  **Предусловие:**
    *   Подготовлен сет из 10 фото (5 качественных фото одежды, 3 фото при плохом свете, 2 фото "не одежды" — например, стул).
2.  **Шаги:**
    *   Загрузить фото через API или интерфейс "Добавить вещь".
    *   Проверить присвоенные теги и характеристики (теплоизоляция, влагозащита).
3.  **Ожидаемый результат:**
    *   Качественные фото: Категория определена верно (Куртка -> Верхняя одежда).
    *   Атрибуты (цвет, длина рукава) распознаны.
    *   Фото "не одежды": Система выдает валидационную ошибку "Одежда не обнаружена", а не добавляет мусорный объект в базу.
